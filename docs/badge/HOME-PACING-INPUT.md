# Home pacing preserves input acquisition opportunities

The shared Home pacing policy no longer depends on slow display transfers to provide touch-sampling opportunities. While waiting for the existing20ms frame interval, it uses the existing `sample_launcher_touch(now,false)` cadence and latches. It never renders, acquires a frame, opens a modal, consumes a pending gesture or changes animation physics. Ordinary pacing may return on a pending launcher swipe; animation pacing retains that action and completes the interval. Provider time counts toward the interval.

All compositions use bounded waits (at most8ms, shortened to the next acquisition opportunity). Contexts remains serviced; crash/modal suppression and existing authority guards remain. Monotonic refusal or terminal touch/Contexts state ends pacing before further context/diagnostic/yield callbacks. Wrap is valid; backward/ambiguous clock movement refuses, and64 repeated no-progress yields stop a stalled clock without spinning. Existing animation duration/progress helpers remain unchanged.

Exact-body tests cover rendering ages0–20/50ms, repeated/coarse clocks,0–2ms provider costs, event phases, ordinary/animation pacing, pending latches, retained touch, monotonic refusal, Contexts refusal, crash/alarm modal suppression, wrap/backward/stopped clocks, and non-launcher compositions. Existing214 animation cases pass in normal and ASan/UBSan lanes. The selected target macro composition is compiled separately; full product qualification belongs to integration.
